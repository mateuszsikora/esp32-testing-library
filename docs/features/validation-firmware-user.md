# Validation firmware

The validation images are the firmware the test suite runs: ESP-IDF projects built for the classic
ESP32, unmodified, in ESP-IDF's own container at a pinned version, so that every machine runs the
same binaries, and one Arduino-ESP32 sketch, `arduino_shell`, built with PlatformIO in a pinned
container of its own ([below](#arduino_shell)). A test names an ESP-IDF image with
`pytest.mark.app_path("../firmware/hello_world")`, and the Arduino one with its PlatformIO build
directory, `pytest.mark.app_path("../firmware/arduino_shell", build_dir=".pio/build/esp32dev")`
([pytest plugin](pytest-plugin-user.md)). The GNSS recordings in `recordings/`, which
`nmea_reader` reads, are generated by a script kept beside them
([The GNSS recordings](#the-gnss-recordings)).

## Build the images

```sh
make firmware                    # every image: the ESP-IDF ones, then the PlatformIO one
firmware/build.sh                # every ESP-IDF image, into firmware/<image>/build/
firmware/build.sh nmea_reader    # only the images named
firmware/build.sh --chips        # the images of the other chips, into firmware/<image>/build-<chip>/
firmware/build.sh --chips gpio_echo@esp32c3   # only the ones named
firmware/build-platformio.sh     # arduino_shell, into firmware/arduino_shell/.pio/build/esp32dev/
```

`make test` builds the images that are missing or whose last build did not finish, so the first
`make test` of a checkout needs Docker too, and leaves the others as they are; `make firmware`
builds them all again ([development guide](../guides/development.md)). Builds are incremental: a
build directory made the same way as before is built on, not from scratch.

`FIRMWARE_OUT=DIR firmware/build.sh` puts each image in `DIR/<image>/build/` instead, `DIR`
relative to the directory you run it from. `make firmware` and `make test` always use `firmware/`,
whatever `FIRMWARE_OUT` the shell exports, because the tests read the images there.

## The images of the other chips

`firmware/build.sh --chips` builds some of the same projects for the ESP32-S3, ESP32-C3 and
ESP32-C6, which the runner also emulates ([runner](runner-user.md#chips)), each into
`firmware/<image>/build-<chip>/`, in the same container and at the same ESP-IDF version. A test
names one with its build directory and the chip's devkit profile:

```python
@pytest.mark.app_path("../firmware/gpio_echo", build_dir="build-esp32c3")
@pytest.mark.board_profile("esp32-c3-devkitm")
```

| Image | For | What differs from the classic ESP32's |
|---|---|---|
| `hello_world` | `esp32s3`, `esp32c3`, `esp32c6` | Nothing: the example names the chip it runs on |
| `console_repl` | the three | Nothing |
| `gpio_echo` | the three | Its default lines, GPIO 6 in and 7 out, the `[lines.echo]` set of the chip's devkit profile ([below](#gpio_echo)) |
| `nmea_reader` | the three | Nothing: UART1 on GPIO 5 (RX) and 4 (TX), the devkits' `[uart.gnss]` |
| `nvs_reader` | the three | Nothing |
| `http_request` | the three | Nothing |
| `hello_world_psram` | `esp32s3` | ESP-IDF's `hello_world` with `firmware/hello_world_psram/sdkconfig.defaults`: `CONFIG_SPIRAM=y`, `CONFIG_SPIRAM_MODE_OCT=y`, the octal PSRAM of the S3 devkit's N8R8 module |

The images that need what esp32sim does not model on these chips, deep sleep (`timer_wake`,
`deep_sleep`, `persistence`), an SD card over SPI (`sdspi`, `sd_remount`) or Bluetooth Classic
(`bt_spp_initiator`), are not built for them
([issue #229](https://github.com/mateuszsikora/esp32-testing-library/issues/229)).
`tests/test_chips.py` runs every one of these images.

## `modem_at`

`modem_at` exercises the [modem model](modem-user.md) without a network. Build it with
`firmware/build.sh modem_at`; `make firmware` and `make test` include it. It uses the LilyGO
profile's UART1 at 115200 baud on TX 26/RX 27, PWRKEY 4 and RI 33, fixed in
`firmware/modem_at/main/main.c`.

If RI starts high, it sends a PWRKEY pulse with a nominal 3000 ms delay, prints
`modem_at: powered off RI=0` and waits another 2 s before restarting the modem. It then sends a
pulse with a nominal 100 ms delay and prints `modem_at: powered on RI=1`. An initial `+++` is
followed by AT, echo, SIM, registration, signal, context, functionality, timezone and operator
commands, `AT+COPS=3,2`, `AT+COPS?` and `AT+CCLK?`, a fallback command, then dial/escape using both
`ATD*99#` and `AT+CGDATA="PPP",1`. Each answer
is printed as `modem_at: <command> => <reply>`, or `TIMEOUT` after a read waits a second with
no byte. It prints `modem_at: dialogue complete`, then queries CSQ, CEREG and CCLK repeatedly,
with 250 ms waits, and prints `modem_at: RI=<level>`. The tests change the modem on the test's
clock and read those ordinary console messages. It does not use esp_modem or PPP.

`tests/test_uart_model.py` runs it on `tests/boards/aux-uart.toml` too, a profile whose UART1 on
the same pins is `uart.aux`, with RI pulled down and no modem model: the far end is a model the
test writes, which answers `OK` to every command ([a UART's own
model](pytest-plugin-user.md#a-uarts-own-model)).

## `modem_recovery`

`modem_recovery` runs PPP through `esp_modem` at `modem-v1.4.1`, the revision `pppos_client` fetches,
with lwIP and esp_netif of the pinned ESP-IDF. Build it with `firmware/build.sh modem_recovery`;
`make firmware` and `make test` include it. It uses the LilyGO profile's UART1, PWRKEY 4, RESET 5,
GPIO 12 and RI 33, fixed in `firmware/modem_recovery/main/main.c`. Run it with `modem.network()`.

It holds GPIO 12 high, starts the modem with a nominal 100 ms PWRKEY pulse if RI reads low, and
dials. Once it has an address it prints `modem_recovery: connected` and sends an NTP request to
`10.64.0.1` about every second while they are answered, and every 2 s when they time out, after 1 s. `IP_EVENT_PPP_LOST_IP` prints `modem_recovery: lost ip`, and ten requests in a row without an answer
print `modem_recovery: no answer`. Either way it then leaves data mode with `esp_modem_set_mode` and sends `AT`. If
the modem answers, it prints `modem_recovery: command mode <reply to AT+CEREG?>` and dials again.
If it does not, it prints `modem_recovery: hung RI=<level>` and runs the
[recovery procedure](modem-user.md#a-hung-modem-and-reset): a nominal 3000 ms PWRKEY pulse unless
RI reads low, then `modem_recovery: after PWRKEY RI=<level>`; GPIO 12 low for 1 s and back up; RESET
high for 2600 ms; 10 s later a 100 ms PWRKEY pulse, then `modem_recovery: recovered RI=<level>`. It
dials again. A dial that gets no `CONNECT` is followed by the same `AT`, and so is one that gets no
address within 30 s, once it has left data mode.

On v5.3.6 a hung modem takes about 35 s from `modem_recovery: no answer` to `modem_recovery: hung`:
`esp_modem`'s `exit_data` waits for lwIP's Terminate-Requests to run out, 12 s here, then 2 s; three
rounds of a 1 s pause, `+++`, 5 s and `\n` `AT`, which waits 0.5 s; then 1 s, and the firmware's own
`AT`, which waits 0.5 s. After `modem.drop_call()` it takes about 21 s
to `modem_recovery: no answer` and 41 s to the next dial, and after `modem.drop_call(terminate=True)`
6 s to `modem_recovery: lost ip` and 14 s to the next dial. No part of this is the model's; it is
the firmware's own timing.

## `nvs_reader`

`nvs_reader` reads namespace `config` from the default `nvs` partition at boot, without
writing or erasing it. Supply `broker_host` (string, at most 255 UTF-8 bytes), `broker_port`
(`u16`), `enabled` (`u8`), `count` (`u32`), `delta` (`i32`), `small` (`i8`), `medium` (`i16`),
`total` (`u64`), `offset` (`i64`) and `broker_ca` (binary, at most 256 bytes) with
[`board.nvs()`](flash-contents-user.md). It prints:

```text
nvs_reader: host=broker.test port=8883 enabled=255 count=4294967295 delta=-2147483648
nvs_reader: small=-128 medium=-32768 total=18446744073709551615 offset=-9223372036854775808
nvs_reader: blob=00ff0d0a434180
```

The blob line is hexadecimal. A missing key, wrong type or oversized value fails an
`ESP_ERROR_CHECK` and aborts the firmware. `tests/test_nvs_reader.py` supplies the values
before power-on and checks the real firmware's output.

## `persistence`

`persistence` shows what a boot finds of the boots before it, for the tests of
[resets and power cycles](pytest-plugin-user.md#resets-and-power-cycles). Build it with
`firmware/build.sh persistence`; `make firmware` and `make test` include it. At every boot it
adds one to `boots` (`u32`) in NVS namespace `persistence` of the default `nvs` partition, to a
count in RTC slow memory (`RTC_NOINIT_ATTR`) and to one in RAM (`__NOINIT_ATTR`); a count whose
marker word is not there starts again at 1. With a FAT card in the `esp32-devkitc` profile's slot
(SCLK 14, MOSI 15, MISO 2, CS 13) it appends `boot N` to `/BOOTS.TXT` and counts the file's lines;
without one, `sd` is -1. It prints:

```text
persistence: boot=2 reason=3 rom=12 rtc=2 ram=2 sd=2 uptime_ms=63
```

`reason` is `esp_reset_reason()` (1 power-on, 3 software restart), `rom` the ROM's reset reason
for core 0, `esp_rom_get_reset_reason(0)` (1 `POWERON_RESET`, 12 `SW_CPU_RESET`), and `uptime_ms`
`esp_timer_get_time()` in milliseconds, the firmware's time since its boot. On the boot NVS counts
as the first it prints `persistence: restarting` and calls `esp_restart()`; on every other boot it
prints `persistence: done` and returns. `tests/test_power.py` runs it, and
`tests/test_flash_snapshot.py` reads `boots` from its flash.

## `ota_state`

`ota_state` goes through an OTA update and a rollback with no network, for the tests of
[`snapshot.ota()`](flash-contents-user.md#read-the-flash-of-a-run). Build it with
`firmware/build.sh ota_state`; `make firmware` and `make test` include it. Its table is ESP-IDF's
`partitions_two_ota.csv`, a `factory` app and `ota_0` and `ota_1`, and rollback is on
(`CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE`). At each step it prints one line, then stands still for
200 ms for a test to read the flash:

```text
ota_state: booted running=factory boot=factory state=none
ota_state: updated running=factory boot=ota_0 state=none
ota_state: booted running=ota_0 boot=ota_0 state=pending_verify
ota_state: marked_valid running=ota_0 boot=ota_0 state=valid
ota_state: updated running=ota_0 boot=ota_1 state=valid
ota_state: booted running=ota_1 boot=ota_1 state=pending_verify
ota_state: rolling_back running=ota_1
ota_state: booted running=ota_0 boot=ota_0 state=valid
ota_state: done running=ota_0 boot=ota_0 state=valid
```

`running` is `esp_ota_get_running_partition()`, `boot` `esp_ota_get_boot_partition()`, and `state`
the running image's `esp_ota_get_state_partition()`, `none` for the factory app, which has none. An
`updated` line comes once the copy is in the next slot and selected, before it restarts. It stops at
`done`. `tests/test_ota_state.py` runs it, also with a power cycle before `ota_1` has confirmed
itself, which boots `ota_0`.

## `timer_wake`

`timer_wake` checks that a deep sleep with a timer wake ends in a boot of its own. Build it with
`firmware/build.sh timer_wake`; `make firmware` and `make test` include it. At every boot it adds
one to a count in RTC slow memory (`RTC_DATA_ATTR`), which the bootloader loads at every boot but a
wake from deep sleep, and prints:

```text
timer_wake: boot=2 rom=5 wake=4
```

`rom` is the ROM's reset reason for core 0, `esp_rom_get_reset_reason(0)` (1 `POWERON_RESET`, 5
`DEEPSLEEP_RESET`), and `wake` is `esp_sleep_get_wakeup_cause()` (0 none, 4 the timer). On its
first two boots it prints `timer_wake: sleeping 2000 ms`, arms a 2 s timer wake and calls
`esp_deep_sleep_start()`; on the third it prints `timer_wake: done` and returns.
`tests/test_timer_wake.py` runs it.

## `deep_sleep`

ESP-IDF's example as it is, with the `sdkconfig.defaults` it ships: the CPU at 80 MHz, the RTC
slow clock on its internal RC oscillator, and the bootloader skipping the image's validation on a
wake. Build it with `firmware/build.sh deep_sleep`; `make firmware` and `make test` include it.
It arms three wake sources, a 20 s timer, EXT1 on GPIO 2 and 4, and touch pads 8 and 9, then
sleeps a second after `app_main`:

```text
Enabling timer wakeup, 20s
Enabling EXT1 wakeup on pins GPIO2, GPIO4
Touch pad #8 average: 1000, wakeup threshold set to 900.
Touch pad #9 average: 1000, wakeup threshold set to 900.
Enabling touch pad wakeup
Not a deep sleep reset
Entering deep sleep
```

On esp32sim only the timer wakes it, 20 s after `Entering deep sleep`, through a
`DEEPSLEEP_RESET`; after the boot it prints the sleep it measured on its RTC, from its clock
before the sleep to its clock after the wake, and sleeps again:

```text
Wake up from timer. Time spent in deep sleep: 20142ms
```

`tests/test_deep_sleep.py` runs it through two sleeps with
[`board.wait_for_wake`](pytest-plugin-user.md#waking-from-deep-sleep).

## `bt_spp_initiator`

ESP-IDF's example as it is, with the `sdkconfig.defaults` it ships: Bluedroid with Bluetooth
Classic and SPP, no BLE, and the controller for BR/EDR alone (`CONFIG_BTDM_CTRL_MODE_BR_EDR_ONLY`,
mode 2), and its own Kconfig defaults: the peer's name `ESP_SPP_ACCEPTOR`
(`CONFIG_EXAMPLE_PEER_DEVICE_NAME`) and Secure Simple Pairing on (`CONFIG_EXAMPLE_SSP_ENABLED`).
Build it with `firmware/build.sh bt_spp_initiator`; `make firmware` and `make test` include it. It
needs a run with [`board.bluetooth`](bluetooth-peer-user.md#in-front-of-the-firmware-boardbluetooth),
which gives the firmware its controller; its project is called `bt_spp_initiator_demo`, and so are
its files.

It starts one inquiry, 30 × 1.28 s long, and looks in each device's extended inquiry response for
the name. On finding it, it stops the inquiry, finds the SPP service with SDP, and opens it with
`ESP_SPP_SEC_AUTHENTICATE`; asked for a PIN in a legacy pairing it answers `1234`. Once the channel
is open it writes `ESP_SPP_MAX_MTU`, 990 bytes, at a time, the bytes 0, 1, 2, … in turn, as fast as
the channel takes them, and every 3 s or more prints what it measured. Against an `SppPeer` with the
PIN `1234` (`tests/test_bt_spp_initiator.py`):

```text
I (883) SPP_INITIATOR_DEMO: ESP_BT_GAP_DISC_RES_EVT
I (883) SPP_INITIATOR_DEMO: ESP_SPP_ACCEPTOR
I (1153) SPP_INITIATOR_DEMO: ESP_SPP_DISCOVERY_COMP_EVT scn_num:1
I (1153) SPP_INITIATOR_DEMO: -- [0] scn:1 service_name:Serial Port
I (1313) SPP_INITIATOR_DEMO: Input pin code: 1234
I (1353) SPP_INITIATOR_DEMO: authentication success: ESP_SPP_ACCEPTOR
I (1373) SPP_INITIATOR_DEMO: ESP_SPP_OPEN_EVT handle:129 rem_bda:[00:00:00:00:5b:01]
I (4393) SPP_INITIATOR_DEMO: speed(1.272643s ~ 4.292801s): 298.951263 kbit/s
```

With another PIN on the peer the authentication fails, `authentication failed, status:9`, and the
link closes before the channel opens. With nobody named `ESP_SPP_ACCEPTOR` on the air the inquiry
runs its 38.4 s, `ESP_BT_GAP_DISC_STATE_CHANGED_EVT` at its start and at its end, and the firmware
starts no other: it then waits for ever. It does not page or pair with a device it finds by
another name.

With Secure Simple Pairing on the peer ([Bluetooth peer](bluetooth-peer-user.md#secure-simple-pairing))
it pairs that way, with a keyboard only (`ESP_BT_IO_CAP_IN`), the IO capability `main.c` sets. A
peer with `io_capability="no_input_no_output"` pairs by Just Works, which Bluedroid allows by
itself: the firmware prints no PIN and no number, `authentication success: ESP_SPP_ACCEPTOR`, and
streams as with the PIN. A peer with a display shows a passkey and the firmware asks for it,
`ESP_BT_GAP_KEY_REQ_EVT Please enter passkey!`; it reads the answer, `spp key …;`, and `spp ok;`
for a number to confirm, on UART0 (`main/console_uart.c`), which the run cannot write
([`console.write` is postponed](../decisions/harness.md#consolewrite-is-postponed-until-the-runner-reads-input)), so Bluedroid gives up 35 s later,
`authentication failed, status:9`, and opens nothing.

## `bt_spp_initiator_psram`

The same example, unmodified, with two options on top of the ones it ships, in
`firmware/bt_spp_initiator_psram/sdkconfig.defaults`: `CONFIG_SPIRAM=y`, PSRAM on, and
`CONFIG_BT_ALLOCATION_FROM_SPIRAM_FIRST=y`, with which Bluedroid takes its buffers from PSRAM
first, as a firmware short of internal RAM does. Build it with
`firmware/build.sh bt_spp_initiator_psram`; `make firmware` and `make test` include it. Its files
are called `bt_spp_initiator_demo`, as the plain image's are. It needs a board profile with
`psram_mb = 4`, as `lilygo-t-a7670g-r2`; the firmware then logs `esp_psram: Found 4MB PSRAM
device`.

Every HCI packet its Bluedroid sends lies in PSRAM, which esp32sim at the pin takes
([Bluetooth peer](bluetooth-peer-user.md#in-front-of-the-firmware-boardbluetooth)). Against the
same `SppPeer` as the plain image it pairs, opens the channel and streams at the same speed:
`authentication success: ESP_SPP_ACCEPTOR` 1.418 s after power-on, the channel at 1.437 s, and
`speed(1.272723s ~ 4.292856s): 298.953674 kbit/s`. Its test in `tests/test_bt_spp_initiator.py`
asks for what the plain image's does.

## `sdspi`

ESP-IDF's example as it is, with its default `sdkconfig`: SPI2 with SCLK on GPIO 14, MOSI 15,
MISO 2 and CS 13, which are the `esp32-devkitc` profile's SD card slot
([board profiles](board-profiles-user.md)), DMA on (`SDSPI_DEFAULT_DMA`), 20 MHz, and no
formatting of a card it cannot mount. It mounts the card at `/sdcard`, prints the card's
registers, writes `hello.txt` with `Hello NAME!`, NAME the product name in the card's CID,
deletes `foo.txt` if there is one, renames `hello.txt` to `foo.txt`, reads it back, writes and
reads `nihao.txt` the same way, and unmounts. With the runner's card, whose CID names it
`SIMSD`, its console ends:

```text
I (105) example: Read from file: 'Hello SIMSD!'
I (105) example: Opening file /sdcard/nihao.txt
I (105) example: File written
I (105) example: Reading file /sdcard/nihao.txt
I (105) example: Read from file: 'Nihao SIMSD!'
I (105) example: Card unmounted
```

and the image holds `FOO.TXT` and `NIHAO.TXT`. A card without a file system ends in
`Failed to mount filesystem.`, an empty slot in
`Failed to initialize the card (ESP_ERR_TIMEOUT). Make sure SD card lines have pull-up resistors in place.`
`tests/test_sdspi.py` runs all three ([pytest plugin](pytest-plugin-user.md#the-fixtures)).

## `sd_remount`

`sd_remount` keeps writing to an SD card that may come and go. Build it with
`firmware/build.sh sd_remount`; `make firmware` and `make test` include it. Its card is on the
`esp32-devkitc` profile's slot, the `sdspi` example's pins (SCLK 14, MOSI 15, MISO 2, CS 13), fixed
in `firmware/sd_remount/main/main.c`; SPI2 is initialised once, with DMA, and stays so.

With a card mounted at `/sdcard` it appends the next line number to `LOG.TXT` every 100 ms,
closing the file each time, and prints the line once the file is closed. The first failure to
open, write or close the file prints the error, unmounts the card, and does not count the line,
which it writes again on the next card. Without a mounted card it tries to mount one every
200 ms, and prints a mount failure once for each run of failed attempts. It never formats a card.

```text
sd_remount: mounted 1
sd_remount: wrote 1
sd_remount: wrote 2
sd_remount: wrote 3
sd_remount: write failed (I/O error)
sd_remount: no card (ESP_ERR_TIMEOUT)
sd_remount: mounted 2
sd_remount: wrote 4
```

`tests/test_sd_remount.py` takes the card out, puts another in, takes that out and puts the
first back while it runs, and starts it with an empty slot
([pytest plugin](pytest-plugin-user.md#taking-the-card-out-and-putting-one-in)).

## `nmea_reader`

`nmea_reader` listens to a GNSS receiver on UART1 and prints a line on its console (UART0) for
every position fix, first

```text
nmea_reader: UART1 RX GPIO5 TX GPIO4 9600 baud
```

once its UART is set up, then

```text
fix acquired lat=52.229677 lon=21.012233
fix lat=52.229657 lon=21.012260
```

`fix acquired` for the first fix, `fix` for each one after it, latitude and longitude in decimal
degrees with six decimals, south and west negative. The two lines above are what the first two
sentences of `recordings/gnss-generated-1.jsonl` print.

A fix is a `GGA` sentence with a fix quality other than `0`, or an `RMC` sentence with status `A`,
from any talker (`$GPGGA`, `$GNRMC`, ...), with a correct checksum, a UTC time and a well-formed
position. A `GGA` and an `RMC` with the same UTC time are one fix and print one line. Everything
else is ignored without a word: other sentence types, a wrong checksum, no fix, an empty or
malformed position, and a sentence longer than NMEA's 82 characters. `nmea_reader` never
transmits; it sets up the TX pin only because the route has one.

The UART comes from `sdkconfig`, menu `nmea_reader` in `idf.py menuconfig`. The defaults are the
GNSS route of the `esp32-devkitc` board profile:

| Option | Default | Range |
|---|---|---|
| `CONFIG_NMEA_READER_UART_PORT` | `1` | 1 to 2 |
| `CONFIG_NMEA_READER_UART_RX_PIN` | `5` (the receiver's TX) | 0 to 39 |
| `CONFIG_NMEA_READER_UART_TX_PIN` | `4` (the receiver's RX) | 0 to 33 |
| `CONFIG_NMEA_READER_UART_BAUD` | `9600` | 1200 to 921600 |

The ranges let through pins that cannot work: GPIO 1 and 3 carry the console's UART0, and GPIO 6
to 11 the SPI flash. `firmware/build.sh` builds with the defaults. A run in the emulator
configures UART1 about 50 emulated milliseconds after power-on. A build at another baud than the
profile's fails every replay into it, on the first frame error
([replay](replay-user.md#what-a-replay-does)).

To watch it on a terminal, outside pytest ([the `esp32tl` command](cli-user.md)):

```sh
esp32tl replay --app firmware/nmea_reader --interface gnss \
  --recording recordings/gnss-generated-1.jsonl --max-seconds 10
```

## `gpio_echo`

`gpio_echo` reads one GPIO line and drives another to the same level, and says so on its console:

```text
gpio_echo: in GPIO33 out GPIO4
in=0
```

the first line once its lines are set up, then `in=` and the input's level, at boot and at every
change after it. It drives the output to that level before it prints the line. Built for the ESP32-S3, ESP32-C3 or
ESP32-C6, it prints `gpio_echo: in GPIO6 out GPIO7`. A change raises an
interrupt on either edge, and the level is read again when the task gets to it, so a change that
comes back before then prints nothing. In the emulator the output is driven low about 44 emulated
milliseconds after power-on, and follows a change of the input within 9 emulated microseconds.

The input has the chip's own pulls off, so an undriven input reads what the board's wiring gives
it. Its defaults are the `[lines.modem]` set of the `lilygo-t-a7670g-r2` board profile: it reads
RI, which the board pulls down, and drives PWRKEY. It is tested on that profile
([pytest plugin](pytest-plugin-user.md#the-fixtures)). The lines come from `sdkconfig`, menu
`gpio_echo` in `idf.py menuconfig`:

| Option | Default | Range |
|---|---|---|
| `CONFIG_GPIO_ECHO_IN_PIN` | `33` (the modem's RI) on the classic ESP32, `6` on the other chips | 0 to 39 |
| `CONFIG_GPIO_ECHO_OUT_PIN` | `4` (the modem's PWRKEY) on the classic ESP32, `7` on the other chips | 0 to 33 |

As for `nmea_reader`, the ranges let through pins that cannot work: GPIO 1 and 3, the console's,
6 to 11, the SPI flash's, and 20, 24 and 28 to 31, which the classic ESP32 does not have, for which
`gpio_config` fails and `ESP_ERROR_CHECK` aborts the firmware at boot.

## What a build leaves

`firmware/<image>/build/` holds an ESP-IDF build directory, the layout pytest-embedded's `IdfApp`
reads: the ELF, the binaries, `config/sdkconfig.json`, and `flasher_args.json`, which gives each
binary's flash offset and from which the backend builds the runner's `--flash-at` arguments. For
every image those are:

| Offset | File |
|---|---|
| `0x1000` | `bootloader/bootloader.bin` |
| `0x8000` | `partition_table/partition-table.bin` |
| `0xd000` | `ota_data_initial.bin`, for `ota_state` only |
| `0x10000` | `IMAGE.bin` (`hello_world.bin`, `nmea_reader.bin`, `gpio_echo.bin`, `sd_remount.bin`, `modem_at.bin`, `modem_recovery.bin`, `nvs_reader.bin`, `pppos_client.bin`, `mqtt_session.bin`, `http_request.bin`, `persistence.bin`, `ota_state.bin`, `timer_wake.bin`, `deep_sleep.bin`), `sd_card.bin` for `sdspi`, `bt_spp_initiator_demo.bin` for `bt_spp_initiator` and `bt_spp_initiator_psram` |

and the ELF is `IMAGE.elf`, `sd_card.elf` for `sdspi` and `bt_spp_initiator_demo.elf` for
`bt_spp_initiator` and `bt_spp_initiator_psram`: the files take the project's name, and those two examples' projects are called
`sd_card` and `bt_spp_initiator_demo`. Two more files say how the build was made:
`esp32tl-build.json` (the ESP-IDF version, the container, and the project it was built from) and
`esp32tl-built`, present only when the build finished. `firmware/**/build/` is ignored by git.

## What it needs: Docker

The build runs in `espressif/idf:v5.3.6`, pinned by digest. It needs Docker Desktop or a rootful
Docker Engine whose daemon answers `docker info`:

- Under rootless Docker or Podman, the files the build writes belong to another uid.
- With SELinux in enforcing mode, the container cannot read the repository.

Neither is supported. The first build pulls the image, 7 GB once unpacked; on a machine that has
it, building `hello_world` from scratch takes a couple of minutes.

## Build with a local ESP-IDF

To iterate without the container, source the `export.sh` of a local ESP-IDF, then:

```sh
IDF_LOCAL=1 firmware/build.sh
```

That ESP-IDF need not be v5.3.6, so it is not for goldens: those come from the container build
only. The build says so on stderr, with the version `idf.py --version` reports and `$IDF_PATH`:

```text
firmware/build.sh: IDF_LOCAL=1, ESP-IDF VERSION at IDF_PATH; not for goldens, which come from the container (v5.3.6)
```

`esp32tl-build.json` then records `"container": null`. Switching between a local and a container
build, or to another ESP-IDF version or install, removes the build directory and builds from
scratch. These two lines go to stdout, `DIR` being the absolute path of the build directory:

```text
firmware/build.sh: hello_world: DIR was built another way, removing it
firmware/build.sh: hello_world built in DIR (ESP-IDF VERSION)
```

The second one ends every finished build.

## What the tests accept

`tests/test_firmware_images.py` reads `firmware/hello_world/build/`,
`firmware/nmea_reader/build/`, `firmware/gpio_echo/build/`, `firmware/sdspi/build/`,
`firmware/sd_remount/build/`, `firmware/nvs_reader/build/`, `firmware/persistence/build/`, `firmware/ota_state/build/`, `firmware/modem_recovery/build/`, `firmware/pppos_client/build/`, `firmware/mqtt_session/build/` and `firmware/http_request/build/`,
and for each:

- passes on a build from the pinned container;
- passes on a local build (`IDF_LOCAL=1`), with the warning
  `IMAGE was built with a local ESP-IDF VERSION, not in CONTAINER`;
- fails on a build from another container or ESP-IDF version, such as one made before the pin
  changed;
- fails when there is no finished build.

The two failures read:

```text
IMAGE was built in CONTAINER (ESP-IDF VERSION), not in PINNED (PINNED_VERSION): run make firmware
DIR holds no finished build: run make firmware
```

`make test` does not rebuild an image that is finished but stale, so after a change of the pin
run `make firmware`.

## When the build stops

`firmware/build.sh` exits 1 with one of these on stderr, before writing anything, or with the exit
code of `idf.py` when the build itself fails:

- `firmware/build.sh: unknown image 'NAME'; the images are: hello_world nmea_reader gpio_echo sdspi sd_remount modem_at modem_recovery nvs_reader pppos_client mqtt_session http_request persistence ota_state timer_wake deep_sleep bt_spp_initiator bt_spp_initiator_psram`
- `firmware/build.sh: needs Docker, or IDF_LOCAL=1 to build with a local ESP-IDF`
- `firmware/build.sh: the Docker daemon is not reachable ('docker info' failed); is Docker running?`
- `firmware/build.sh: IDF_LOCAL=1 needs ESP-IDF in the environment: source $IDF_PATH/export.sh first`

The rest are in [Failure modes](validation-firmware-technical.md#failure-modes).

## The GNSS recordings

`recordings/gnss-generated-1.jsonl` and `recordings/gnss-generated-2.jsonl` are what a GNSS
receiver on the `esp32-devkitc` profile's `uart.gnss` route would send `nmea_reader`, in the
[recording format](../recording-format.md). Each is a
stationary receiver with a fix from its first sentence: one sentence per emulated second, `$GPGGA`
and `$GPRMC` in turn, the first at 1 s and the last at 60 s, the position wandering a few metres
around its start. At 9600 baud a sentence takes under 80 ms on the wire.

| Recording | Seed | Starts at | First line `nmea_reader` prints |
|---|---|---|---|
| `gnss-generated-1.jsonl` | 1 | Warsaw, `5213.7806,N` `02100.7340,E` | `fix acquired lat=52.229677 lon=21.012233` |
| `gnss-generated-2.jsonl` | 2 | Buenos Aires, `3436.2220,S` `05822.8960,W` | `fix acquired lat=-34.603700 lon=-58.381600` |

The second recording is somewhere else, in the other two hemispheres, so a test can tell which
one the firmware read.

`scripts/generate-gnss-recordings.py` writes both from fixed seeds, and writes the same bytes
every time, on any machine, with Python 3.9 or newer (the system `python3` of macOS) and nothing
else:

```sh
python3 scripts/generate-gnss-recordings.py           # write them
python3 scripts/generate-gnss-recordings.py --check   # exit 1 if a committed one differs
```

Writing prints `scripts/generate-gnss-recordings.py: wrote recordings/NAME` for each. `--check`
writes nothing and prints, for each recording that differs or is missing:

```text
scripts/generate-gnss-recordings.py: recordings/NAME is not what the script generates; run python3 scripts/generate-gnss-recordings.py
```

To change a recording, change the script and run it; `tests/test_gnss_recordings.py` fails while
the committed files differ from what it writes. A test replays one into the firmware with
`gnss.replay(path)` ([replay](replay-user.md#replaying-a-gnss-recording)).

## pppos_client

`firmware/build.sh pppos_client` builds esp-protocols' unmodified
`components/esp_modem/examples/pppos_client` at `modem-v1.4.1`
(commit `2cc7c99664caf9705064affba6ea829137d4e1e8`). It is also included in `make firmware`
and `make test`. The first build downloads the source archive; firmware tests require no host
network. `firmware/pppos_client/sdkconfig.defaults` selects SIM7600 AT commands, UART TX 26,
RX 27, no flow control, and 4 MB flash. The route matches `lilygo-t-a7670g-r2` at 115200 baud.
The upstream MQTT URI, topic and payload are unchanged: `mqtt://mqtt.eclipseprojects.io`,
`/topic/esp-pppos`, `esp32-pppos`.

The image lands at `firmware/pppos_client/build/`, with the same provenance and finished-build
marker as other images. `tests/test_pppos_client.py` checks the firmware publishing and receiving
from the test's broker. [The network guide](network-user.md) shows both tests. This example uses
plain MQTT; tracker firmware TLS/NTP validation is #72.

## mqtt_session

`firmware/build.sh mqtt_session` builds `firmware/mqtt_session`, on the LilyGO modem route at 115200
baud, with the pinned esp_modem that `pppos_client` downloads. It is included in `make firmware` and
`make test`. It dials, resolves `broker.test` and connects esp-mqtt with
`.session.disable_clean_session = true`, the client ID `session-client` and a reconnection after
1 s (`.network.reconnect_timeout_ms`), then subscribes to `session/commands` at QoS 1 on every
connection, as a client that does not trust the session would. It prints:

```text
mqtt_session: connected session_present=0
mqtt_session: data dup=0 qos=1 id=1 topic=session/commands payload=hello
mqtt_session: disconnected
```

`session_present` is `event->session_present` of `MQTT_EVENT_CONNECTED`, and `dup`, `qos` and `id`
are those of `MQTT_EVENT_DATA` (ESP-IDF v5.3.6, `components/mqtt/esp-mqtt/include/mqtt_client.h`).
Told `backlog <n>` on `session/commands`, it publishes `report 1` to `report <n>` on
`session/reports` at QoS 1, one at a time, waiting for `MQTT_EVENT_PUBLISHED` of each, and prints
`mqtt_session: published <k> of <n>`, then `mqtt_session: backlog done`. A command that comes with
DUP starts nothing.

`tests/test_mqtt_session.py` runs it against the test's broker
([keep a session across connections](network-user.md#keep-a-session-across-connections),
[give the network a round trip and a rate](network-user.md#give-the-network-a-round-trip-and-a-rate)).

## `http_request`

`firmware/build.sh http_request` builds ESP-IDF v5.3.6's `examples/protocols/http_request`,
unmodified and with no `sdkconfig` change, so it takes ESP-IDF's defaults: Wi-Fi
(`EXAMPLE_CONNECT_WIFI=y`), SSID `myssid` (`EXAMPLE_WIFI_SSID`) and passphrase `mypassword`
(`EXAMPLE_WIFI_PASSWORD`). `make firmware` and `make test` include it. The first build copies the
example, unchanged, to `firmware/.http_request-v5.3.6/` (`.http_request-<version>` for the ESP-IDF
version that builds it, under `FIRMWARE_OUT` when that is set; git ignores it) and builds the copy: the example takes `protocol_examples_common` through the component manager,
which writes `dependencies.lock` into the project, and ESP-IDF's examples are read-only in the
container. The copy is made once per ESP-IDF version and reused.

It joins the access point, then in a loop resolves `example.com`, connects to port 80, sends

```text
GET / HTTP/1.0
Host: example.com:80
User-Agent: esp-idf/1.0 esp32
```

prints the whole response, headers and body, as it reads it, then
`... done reading from socket. Last read return=0 errno=<n>.`, counts down from `10... ` to
`0... `, one second apart, prints `Starting again!` and fetches again. While it cannot join it
prints `Wi-Fi disconnected <reason>, trying to reconnect...`: reason 3 when the access point
deauthenticates it as it leaves. In the emulator, with the test's access point, it joins at about
2.79 emulated seconds, has its DHCP lease at 2.80 s and sends its request at 4.13 s.

`tests/test_http_request.py` runs it with the `wifi` fixture
([network](network-user.md#fetch-a-page-behind-a-wi-fi-access-point)): the fetch from the test's
HTTP server, a rejoin after the access point goes off the air and back, no access point, a wrong
password, the report, and `wifi` refused after power-on. `tests/test_determinism.py::test_wifi_http`
runs it twice for [determinism](../guides/testing.md#determinism), and
`tests/test_firmware_images.py::test_http_request_is_esp_idfs_example_with_its_default_wifi` checks
the build's flash layout and its three Wi-Fi options in `config/sdkconfig.json`.

## `http_server`

`firmware/build.sh http_server` builds `firmware/http_server`, this repository's own project, with
ESP-IDF's default `sdkconfig`. `make firmware` and `make test` include it. It joins `myssid` with
`mypassword` over WPA2-PSK, the defaults of ESP-IDF's examples, and joins again whenever it is
disconnected, printing `http_server: Wi-Fi disconnected <reason>`. At its first address it prints
`http_server: got address 10.64.0.2`, starts `esp_http_server` with `HTTPD_DEFAULT_CONFIG()` and
prints `http_server: listening on port 80`; a later address does not start it again.

| Request | Response |
|---|---|
| `GET /status` | `200 OK`, `{"status":"ok","requests":<n>,"uptime_ms":<ms>}`, `<n>` counting this request among those served since boot |
| `POST /echo` with a JSON body | `200 OK`, `{"echo":<the body, parsed>,"bytes":<its length>}` |
| `POST /echo` with a body that is not JSON | `400 Bad Request`, `{"error":"invalid JSON"}` |
| `POST /echo` with a body over 2048 bytes | `413 Content Too Large`, `{"error":"body over 2048 bytes"}` |

Every response is `application/json`. The connection stays open for the next request, unless the
request has `Connection: close`: then the response carries it too, and the server closes the
connection after it. Each response prints `http_server: <method> <uri> -> <status>`, as
`http_server: GET /status -> 200`. Any other path gets `esp_http_server`'s own `404`.

`tests/test_http_server.py` runs it with the `wifi` fixture and is its client
([network](network-user.md#open-a-tcp-connection-to-the-device)): a `GET` closed on request, two
`POST`s on one connection, a body over 2048 bytes, a refused port, connecting before the lease, and
connecting again after a reset and a power cycle.
`tests/test_firmware_images.py::test_http_server_is_a_wifi_station_with_esp_http_server` checks the
build's flash layout.

## `arduino_shell`

`firmware/arduino_shell` is a PlatformIO project, `platformio.ini` and `src/main.cpp`, on the
Arduino-ESP32 core: environment `esp32dev`, `board = esp32dev`, `framework = arduino`, and
pioarduino's espressif32 platform at release `55.03.312-1`, which brings Arduino-ESP32 3.3.12 on
ESP-IDF 5.5.5. Every other image is an ESP-IDF build; this one takes the core's own driver paths,
`HardwareSerial` on UART0, `Preferences` on NVS, `WiFi` and `WebServer`, which a firmware built the
same way takes. `make firmware` and `make test` include it ([below](#build-the-arduino-image)).

It reads its settings once at boot, read-only, from the Preferences namespace `shell`, which a test
writes with `board.nvs(...)` ([flash contents](flash-contents-user.md#supply-nvs-before-power-on)):

| Key | Type | Effect |
|---|---|---|
| `greeting` | string | printed after the banner; empty when missing |
| `ssid`, `password` | strings | the network it joins as a station; without `ssid` it does not start Wi-Fi |

At 115200 baud on `Serial`, every line it prints starts with `arduino_shell: ` and ends with
`\r\n`:

```text
arduino_shell: Arduino-ESP32 3.3.12
[     3][E][Preferences.cpp:47] begin(): nvs_open failed: NOT_FOUND
arduino_shell: greeting=hello from the test
arduino_shell: joining myssid
arduino_shell: ready; type help
```

The second line is the core's own log, there only when the flash holds no namespace `shell`; the
greeting is then empty. `joining` is there only with an `ssid`. A line it receives on `Serial` is a
command, its `\r` before the `\n` dropped and anything past 64 bytes left out:

| Command | Answer |
|---|---|
| `help` | `arduino_shell: commands: help, greeting, uptime, wifi, ap-off, ap-on` |
| `greeting` | `arduino_shell: greeting=<value>` |
| `uptime` | `arduino_shell: uptime_ms=<millis()>` |
| `wifi` | `arduino_shell: wifi=off` without an `ssid`, `arduino_shell: wifi=joining` before it has an address, `arduino_shell: wifi=connected ip=<address>` after |
| anything else, not empty | `arduino_shell: unknown command '<line>'; try help` |

No test sends a command yet: the `console` interface has no `write`, because the runner does not
read input for UART0.

Once it has an address it prints `arduino_shell: listening on <address> port 80`, `10.64.0.2` behind
the `wifi` fixture's access point, and serves `GET /status` with `200 OK` and
`{"status":"ok","requests":<n>,"uptime_ms":<ms>}` as `application/json`, `<n>` counting this request
among those served since boot, printing `arduino_shell: GET /status -> 200`. Any other request gets
`WebServer`'s own `404`, `Not found: <uri>` as `text/html`.

`tests/test_arduino_shell.py` runs it from `firmware/arduino_shell/.pio/build/esp32dev/` as the
build left it: the banner on a flash with no settings, a greeting the test wrote with `board.nvs`,
and `GET /status` through `network.connect(80)` once it joined the `wifi` fixture's access point
([network](network-user.md#open-a-tcp-connection-to-the-device)).
`tests/test_firmware_images.py::test_arduino_shell_is_a_platformio_build_of_the_whole_flash` and
`test_arduino_shell_has_the_arduino_default_table_with_its_nvs` check the build: `firmware.factory.bin`
at `0x0`, the table at `0x8000` with `nvs` at `0x9000`, and `app0` at `0x10000`.

## Build the Arduino image

```sh
firmware/build-platformio.sh                  # every PlatformIO image: arduino_shell
firmware/build-platformio.sh arduino_shell    # the same, by name
PIO_LOCAL=1 firmware/build-platformio.sh      # with the pio on PATH, for iteration
```

The build runs `pio run` in `python:3.13-bookworm`, pinned by digest, with pioarduino's PlatformIO
Core `6.2.0` and the platform `platformio.ini` names. Like the ESP-IDF build, it needs Docker Desktop
or a rootful Docker Engine ([What it needs: Docker](#what-it-needs-docker)), and network access to
GitHub and PyPI for its first build. PlatformIO's core directory, what is `~/.platformio`
elsewhere, is `.cache/platformio/` of the repository: the first build installs PlatformIO Core there,
then the platform downloads its framework and toolchains, 5.7 GB in all; later builds download
nothing. `make clean` keeps it. On an arm64 Mac the first build took 8m52s, a build from scratch with
the core directory there about 80 s, and an incremental one 13 s.

The build leaves PlatformIO's own build directory, `firmware/arduino_shell/.pio/build/esp32dev/`,
which esp32tl loads as it is ([builds](builds-user.md)): `firmware.bin`, `bootloader.bin`,
`partitions.bin`, `firmware.factory.bin` (all of them merged from `0x0`, with the platform's
`boot_app0.bin` at `0xe000`), `firmware.elf` and `firmware.map`, beside PlatformIO's object files.
`esp32tl-build.json` records how it was built (PlatformIO Core's version, the platform, the
container and the project) and `esp32tl-built` is there only when the build finished.
`firmware/**/.pio/` is ignored by git. `FIRMWARE_OUT=DIR` puts the build in
`DIR/arduino_shell/.pio/build/esp32dev/`, with a copy of the project's `platformio.ini` and `src/`
in `DIR/arduino_shell/`.

`PIO_LOCAL=1` builds with the `pio` on `PATH` and its own core directory; that PlatformIO need not
be the pinned one, so it is not for goldens. These lines go to stderr, then stdout:

```text
firmware/build-platformio.sh: PIO_LOCAL=1, PlatformIO Core VERSION; not for goldens, which come from the container (pioarduino 6.2.0)
firmware/build-platformio.sh: arduino_shell: DIR was built another way, removing it
firmware/build-platformio.sh: arduino_shell built in DIR (PlatformIO Core VERSION)
```

`built another way` comes when the last build had another PlatformIO Core, platform, container or
project: the project's whole `.pio/` is removed and the build starts from scratch. The `built in`
line ends every finished build. A container build whose core directory has no PlatformIO Core of
the pinned version first prints
`firmware/build-platformio.sh: installing pioarduino 6.2.0 in /platformio/penv`.

`tests/test_firmware_images.py` accepts the build as it does the ESP-IDF ones
([What the tests accept](#what-the-tests-accept)), with these messages:

```text
DIR holds no finished build: run make firmware
arduino_shell was built with PLATFORM, not PINNED_PLATFORM: run make firmware
arduino_shell was built in CONTAINER (PlatformIO Core VERSION), not in PINNED (PINNED_VERSION): run make firmware
```

and the warning `arduino_shell was built with a local PlatformIO Core VERSION, not in CONTAINER` for
a `PIO_LOCAL=1` build.

`firmware/build-platformio.sh` exits 1 with one of these on stderr, before writing anything, or with
the exit code of `pio` when the build itself fails:

- `firmware/build-platformio.sh: unknown image 'NAME'; the images are: arduino_shell`
- `firmware/build-platformio.sh: needs Docker, or PIO_LOCAL=1 to build with a local PlatformIO`
- `firmware/build-platformio.sh: the Docker daemon is not reachable ('docker info' failed); is Docker running?`
- `firmware/build-platformio.sh: PIO_LOCAL=1 needs PlatformIO's pio on PATH`

The rest are in [Failure modes](validation-firmware-technical.md#failure-modes).

`help` through Arduino `Serial`, exercising its driver path. Both help tests can run on serial

### Arduino SoftAP

`arduino_shell` also reads Preferences keys `ap_ssid` and `ap_password` in namespace `shell`.
With a nonempty `ap_ssid` and no `ssid`, it starts `WiFi.softAP`, open when `ap_password` is empty,
otherwise WPA2-PSK, and serves the same `GET /status` on port 80. A configured `ssid` still takes
precedence and follows the existing station path; there is no timed fallback after a failed join.
Successful AP startup prints `arduino_shell: access point SSID at 192.168.4.1`; failure prints
`arduino_shell: access point failed`. Join and leave events print
`arduino_shell: station MAC joined` and `arduino_shell: station MAC left`, with lowercase MAC
hexadecimal octets. The `wifi` command prints `arduino_shell: wifi=access-point ip=192.168.4.1`.
The HTTP handler still prints `arduino_shell: GET /status -> 200` and returns status, request count
and uptime. Existing console commands and station-mode lines keep their meanings.

`tests/test_arduino_softap.py` exercises open and WPA2 APs, the join MAC, wrong-password timeout
and raw TCP. Build with `firmware/build-platformio.sh arduino_shell`, as for the existing image;
no prebuilt binary is committed.

The Arduino shell accepts unsigned NVS `shell/ap_delay_ms` (`esp32tl.flash.u32`, default 0), delaying SoftAP startup by that many milliseconds. Commands `ap-off` and `ap-on` stop and restart its SoftAP using the configured NVS credentials, for station lifecycle tests.
